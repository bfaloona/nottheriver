# Scale feasibility: what can be cached or stored

Product design feasibility: what in a search can be cached or stored as the site gets users, and what each choice does to freshness, quality, privacy, trust and features. Read-only research, 2026-10-08, branch `main` at 3deed0e. No code changed, no live calls made. Summary and operator questions: [scale-feasibility.md](scale-feasibility.md). Companion (money): [scale-feasibility-costs.md](scale-feasibility-costs.md); this note builds no cost tables and names the reuse choices that matter for cost in section E so the two can be joined.

Builds on `docs/caching-and-store-types.md` (Q1 and the 2026-09-27 triage), which already ranked six cache candidates and recorded operator rulings CQ1 to CQ5 (`docs/caching-and-store-types.md:84-107`). Those rulings are cited, not re-argued; what is new here is the product view (who shares what, what stale looks like to a shopper, what a store would unlock), the database question, and the few facts that have changed since 2026-09-27 (split enrich, the verdict-flip figures, the chain list).

Vocabulary: **cache** = a copy of something the search would otherwise fetch or compute, with an expiry, that the search can live without; **store** = a durable record the product reads as a source in its own right (like `data/*.json` today), with no expiry and a path to edit it.

## A. Inventory: what a search consumes and produces

How the search is wired, for reference: the browser sends product, city, state, a 2-decimal zip-area center and an optional rural-urban code (`proxy/src/contract.ts:7-14`); the Worker reads the product (model call, cached), runs up to 3 web and 2 place searches on Brave with that center (`proxy/src/pipeline.ts:108-115`, `proxy/src/brave.ts:153-177`), judges the candidates in two parallel model calls (`proxy/src/enrich.ts:116-134`), scores deterministically and answers with `Cache-Control: no-store` (`proxy/src/handler.ts:139`). The response carries the queries, both ranked sections, the usage figures and a `dropped` list (`proxy/src/contract.ts:119-131`).

Sharing levels used below: **everyone** (same for any user anywhere), **area** (same for users whose zip rounds to the same 2-decimal center; 111 ZCTAs share a center at that rounding, `docs/debt.md:76`), **one user** (useful only to the person who searched).

Two things the inventory shows that were not in the 2026-09-27 note:

- **Place results are shared across products, not just across people.** Because local wording names a store type, a place cache would serve every product in a category in one zip area. The triage's "sparse" judgment (`caching-and-store-types.md:32`) was about product × area; the real key is store type × area, which is denser by the ratio of products to store types (20 to 26 wordings in the eval, with the big categories, outdoor and kitchen, collapsing 3 to 5 products onto one wording).
- **The verdict's context dependence is now measured.** The split-enrich result (`search-latency.md:113`) shows the same shop gets a different sells-it label depending on what else is in the call. A verdict cache would store whichever context happened first. That is a stronger reason than the 2026-09-26 ruling had available to keep verdicts uncached as a call-skipper, and a reason to think about a narrower use (RQ2).

## B. The database question: store the shop, or store the search

Nothing in the product is a database today. Durable facts live in `data/*.json` (repo, build-time), evidence in `docs/evidence/`, and the only runtime store is the KV cache of product readings. Two different things could become a database, and they have opposite privacy profiles.

### B1. Store the shop

A record per shop (registrable domain; for local, domain plus street address), holding what the repo files hold today plus what only a store can hold:

| Would hold | Exists today as | What a store adds |
|---|---|---|
| Certifications, findings with band and relation fields, chain row, accepted sources | `data/*.json`, one row per domain, PR-reviewed, dated, tested (`proxy/test/data.test.ts`) | Editing without a deploy. Nothing else: the repo path already gives sourcing, dates and review |
| Dispute state per finding or badge: open, under review, upheld, withdrawn, with dates | A GitHub issue from the template (`.github/ISSUE_TEMPLATE/dispute-a-ranking.md`); review process is TBD (`about.html:44`, `STATUS.md:92`, `0004-down-ranking.md:27`) | The page could show "disputed, under review" on the finding, and a withdrawn finding could stop scoring the day it is withdrawn. This is the feature a store unlocks that files cannot, because a dispute is an event, not a fact |
| Corrections: "confirmed closed at this address on date", "does not sell this category", "wrong website on the map listing" | Grader notes in `grades.json` (I12), used only by the eval | The live search could drop a shop a grader confirmed closed (3 of 24 new rows in one run, `quality.md:90`) instead of showing it until Brave notices. Each correction is a sourced, dated, disputable row, the same shape as a finding, so it fits ADR 0004's stance ("every finding shown is curated", `0004-down-ranking.md:15`) |
| Grades joined to live results | Reused by url and address at eval time (`quality.md:91`) | Precision tracking over time: every live result that matches a graded (url, address) could be counted, giving a running "share of shown shops with a good grade" without new grading. It measures only the graded subset, and graded shops skew to the eval's 20 products |
| Shop pages (one page per shop listing its badges, concerns, disputes, and which products it was shown for) | Nothing | A new kind of page. Needs the shop record and, to list products, a (shop, product) history, which is I4-shaped data (a list of products searched) and should be opt-in by design, not a side effect |
| Suggested shops (Amazon plan Phase D) | Planned as a repo file `data/alternatives.json` matched on the normalized category (`docs/plans/amazon-alternatives-in-ranking.md:65`), ruled "not yet" (`:95`, `STATUS.md:50`) | Nothing: Phase D is persistence-shaped but static. It does not need a database; it needs the Q4 ruling |

What it costs:

- **Privacy:** nothing, as long as the record holds facts about shops and never (shop, product, time) rows that come from searches. The moment a shop record says "shown for cast iron skillet 14 times this week" it is a search log by another name.
- **"Every result explained from a source":** a store keeps this if every row carries a source URL, a date and a dispute link, exactly as `data/*.json` rows do. The risk is operational: a database invites quick edits without the data test, the `checked` date and the PR diff. The mitigation is to keep the same row schema and the same test, run against the store.
- **Trust:** stronger, if dispute state is visible. The About page's "How disputes are reviewed and resolved: TBD" (`about.html:44`) is the current gap, and it is a process gap, not a storage gap; the store is worth building only once that process exists.

### B2. Store the search

A row per request: product, center, rural-urban code, the wording used, cache hits, Brave calls, model cost, latency, maybe the response.

| Would unlock | Needs | Cheaper way to get most of it |
|---|---|---|
| Cost accounting per day and the live cache hit rate (unknown today, `search-latency.md:144`) | Counters only | Daily totals: searches, normalize hits, Brave calls, model cost from `usage` (I8). No row per search |
| Popular-product pre-warming of the reading cache (OPT-4, `search-latency.md:144`) | Product text per search, counted | Count by the hash the cache already uses (`normalize-cache.ts:16-20`); still a list of products, which `privacy.md:32` already admits the cache is |
| Abuse detection beyond the 60 s limiter | Client key over longer windows | The Durable Object counter (I13) over a 10-minute window, the alternative `debt.md:11` already names |
| Reproducing a disputed result ("the site showed X for Y on date") | The response per search | Not worth the privacy cost. The eval's saved responses already give a reproducible record for the 60 fixed searches |
| Stage timings in production (OPT-6, `search-latency.md:146`) | Per-request ms per stage | A log line with ms and provider only, as OPT-6 specifies: no query text, no coordinates |

What it costs: the privacy page's "What is kept" table has no row for requests (`privacy.md:27-36`) and the Worker log line is route, status and ms by design (`privacy.md:31`). A search store with product and center is a trail of what was searched where; with IP it is a trail of who. The product text is typed by a stranger and can be anything (`privacy.md:32`). Recommendation: never a row per search; daily totals and the hashed product count at most, each with a `privacy.md` row before it ships.

## C. Product-level tradeoffs

| Choice | What a shopper gets | What a shopper loses | What the About page would have to say |
|---|---|---|---|
| Shared product reading (today) | The same searches for the same product wherever and whoever; disputes about wording are reproducible | The first person's reading sets it for everyone for 30 days (`architecture.md:21`), even if the model would do better next time | Already says it (`about.html:48`) |
| Shared Brave results (I2, I3) | Faster (Brave is under 1 s, `search-latency.md:41`, so not much faster) and cheaper searches; eval repeatability | A closed shop stays "nearby" for the TTL; a missing shop stays missing. The page shows no fetch time, so a shopper cannot tell a 1-hour-old draw from a fresh one | "Shops near you were found within the last N hours" in Coverage (`about.html:51`), and a Privacy sentence that the site keeps search terms with zip-area centers for N hours (`about.html:48`) |
| Shared verdicts (I4) | Faster enrich (median 4.1 s on 2026-10-01, `quality.md:108`; 2.3 s on 2026-09-28, `search-latency.md:107`) only if the call is skipped, which needs every candidate to hit (`caching-and-store-types.md:34`) | User B inherits user A's model verdict, made in a different candidate context. A wrong "no" becomes persistent and invisible; a wrong "yes" is at least visible and gradable. Caching only yes/maybe (the 2026-09-27 suggestion) keeps the drop fresh but then never skips the call | "Whether a shop sells it was judged by the model within the last N days" on the result's "Why this rank" line ("Likely, by shop type, judged <date>"), or the explanation silently ages |
| Full response cache (I10) | Instant repeat searches in dense areas | Everything above at once, and a product-plus-location store | A sentence that the site keeps whole results per product and zip area for N hours; the hardest sentence on this list to write next to "Your zip code never leaves your browser" |
| Shop store with corrections (B1) | Fewer closed or wrong shops; a visible dispute state; a shop page | Nothing a shopper notices, if rows stay sourced and dated. The cost is operator time to run the dispute process | "Disputes: reviewed within N days; a disputed finding is marked while under review" replaces "TBD" |
| Search counters (B2) | Nothing directly; the operator gets cost and hit-rate numbers to decide the rest | Nothing, if counters only | A `privacy.md` row: "daily totals of searches and calls, no product text, no location" |

Freshness promises the product could honestly make today: results come from Brave's index as of the moment of the search (true now, `about.html:51`); the product reading is up to 30 days old (said). Promises it cannot make with any cache: stock ("sells it" was never a stock check, `ranking.md:43`). Promises a place cache would weaken: "nearby shop exists", the one local failure the eval counts hardest.

The asymmetry worth stating plainly for any shared cache: a wrong **keep** is visible (a shopper sees a bad shop and can dispute it), a wrong **drop** is invisible (nobody knows the shop was hidden). The code already fails open for that reason (`architecture.md:27`). Caching inverts the guarantee for drops: a verdict cache or a stale place draw makes a wrong drop last for the TTL, for everyone, with no dispute link because there is nothing on the page to dispute. That holds for verdicts: a verdict cache should hold yes/maybe but never "no". For Brave draws the risk runs the other way: a cached draw is a cached keep, and a stale keep (a closed shop shown as nearby) is the cost; the control is a lifetime measured in hours, not days. Serving a cached draw only alongside a fresh fetch would remove the risk but saves no Brave call, so it is not the cache the costs note prices.

## E. Pointers for the cost agent

The reuse choices most likely to move cost, with the key and the sharing the cost model should assume. Per-search figures are the measured ones in `docs/costs.md:24-31` (Brave at list price, model use measured).

| Label | Choice | Key | Sharing to model | What a hit saves | Notes for the join |
|---|---|---|---|---|---|
| E1 | Place-search cache (I3) | (local query, 2-decimal center) | Store type × zip area: ~26 wordings for 20 products; 2 place calls per search | Up to 2 of the typical 4 Brave calls ($0.010 of about $0.023 at list price) | Ruled no (CQ1); model it as a sensitivity only. Hit rate is a function of searches per zip area per TTL, not per product |
| E2 | Web-search cache (I2) | (online query) if RQ6 shows location does not matter; else (online query, center, city, state) | Everyone per product in the first case; area in the second | Up to 2 to 3 of 4 Brave calls ($0.010 to $0.015) | The first key form is the only Brave cache with no location privacy cost; pending RQ6 |
| E3 | Product-reading cache (I1, exists) | Hashed lowercased product | Everyone per exact product text | One normalize call, $0.00032 to $0.00034, plus 0.9 to 7.8 s (`search-latency.md:40`) | Small money, large latency; hit rate unknown live (RQ4 gets it). KV has daily write limits the code already tolerates (`normalize-cache.ts:36`) |
| E4 | Verdict cache as prompt shrinker (I4, RQ2) | (domain [+ address], product reading), yes/maybe only | Everyone per product | A fraction of the median $0.0034 model use per search; the calls still run | Ruled no (CQ2); sensitivity only. Note the enrich prompt is billed at the throughput-routed endpoint's price, 6.4× the cheapest (`costs.md:18`), so the model share is sensitive to routing, not only to caching |
| E5 | Full-response cache (I10) | (product reading, center, rural-urban code) | Area × product | A whole search on a hit | Expect a near-zero hit rate outside dense areas; include only to show the ceiling |
| E6 | Shared rate-limit counter (I13) | Client key | n/a | Nothing per search; it is a platform cost (Durable Object) and the fix for the per-isolate limiter (`debt.md:10`) | Platform line item, not a cache |
